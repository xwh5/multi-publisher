同一台机器，同一个 .NET 项目，写 1000 个小文件：WSL 原生文件系统用了 0.05 秒，放在 Windows 盘上经 /mnt 桥接访问用了 8.8 秒——慢 169 倍 [S1]。

不是某个文件偶尔抽风。这是每个文件操作（open/stat/read/write/close）都要经 9p 协议跨 Linux↔Windows 边界翻译一次的协议成本，你逃不掉。

我做了两轮实测：第一轮，在自己的开发机上把项目放在三种位置跑了九项对照；第二轮，为了搞清楚 WSL 到底是个什么玩意，我把公司 VPN 环境下的 WSL 网络链路整个重配了一遍，踩了两个版本的假验证坑。结论只有一句——项目进 WSL 原生 ext4，工具进 WSL，别走 /mnt 桥接。我的判断基于 169× 实测、微软官方文档原文和六个社区来源的独立复现。

先记住结论

同一台机器，项目放对地方：warm build 2.63s；放错地方：直接卡死崩溃。

一、三种放法，三种命运

项目可以放三个地方 [S1]：

方式 路径 文件系统 命运
Windows 原生 C:\Dev\my-project NTFS 正常，warm build 4.23s
WSL 走 /mnt 项目在 C 盘，WSL 里 /mnt/c/... 访问 NTFS 桥接 重负载直接卡死
WSL 原生 ~/work ext4 warm build 2.63s，比 Windows 还快

最坑的是第二种。grep 慢 15×，write1000 慢 169×，git status（300 个未跟踪文件）明显劣化——这些你都还能忍。真正爆掉的是 dotnet build：第一次全量编译勉强出数字，重跑一次，obj/bin 上千个中间文件全部走 9p，直接超时崩溃 [S1]。

对 AI 编程来说这个坑被放大了。opencode、Cursor 这类 agent 的日常不是写代码，是海量小操作：rg --files、git status、dotnet restore、读文件、写文件。模型再聪明，工具链卡在 9p 桥接上，每一步都在付协议税。你花几万块买的 token 额度，相当一部分烧在了「跨边界翻译」上。

二、为什么慢：WSL2 是台独立虚拟机

WSL2 不是 Windows 的"子系统"，是一台跑在轻量虚拟机里的真 Linux，有自己的真 ext4 [S1]。访问 ~/ 是原生速度；访问 /mnt/c，每个文件操作都经 9p 协议翻译一次 [S1]。

微软官方文档原话："For the fastest performance speed, store your files in the WSL file system if you are working in a Linux command line" [S4]。官方不建议跨文件系统工作——这不是玄学，是架构使然。

一个常被忽略的推论：WSL1 在跨系统访问上反而比 WSL2 快，因为 WSL1 是 API 翻译层，没有虚拟机边界；WSL2 的快只对原生文件系统成立，官方给出的提升是 git clone / npm install / cmake 快 2-5×、解压 tarball 快 20×——全部在 VHD 内部 [S5]。

独立到什么程度？我自己的例子。公司 aTrust VPN 的 WFP 驱动只拦截 Windows 进程发起的连接，WSL 里的进程一个都不管 [S13]。这意味着 WSL 侧必须自己搭一条链路（mihomo TUN + 域名还原转发给 Windows Clash）才能连内网。我把这套方案从 v1 一路迭代到 v4，两版假验证的坑都踩过 [S13]。WSL 有独立的网络栈、独立的 systemd、独立的 DNS——它是台完整的虚拟机，跨边界的每一样东西都有成本，文件系统只是最显眼的那一个。

为什么 grep 只慢 15×，write1000 却慢 169×？单次大批量顺序读（一次 rg 扫全项目），9p 的往返开销摊薄了；大量独立小文件操作，每个文件都要 open/stat/write/close 各付一次翻译成本，误差累积成灾难 [S1]。

三、破除误区，学会验证

误区一：「WSL 的 build 慢」是假的

我初测时见过 41s、54s、甚至 205s 的数字，一度怀疑 WSL 环境有问题 [S1]。逐层拆开：连续无改动 build 稳定在 ~5.5s，其中 user 5s、sys 仅 1.5s——时间花在 CPU 计算上，不是文件系统。那 ~5s 固定成本来自 Mediator.SourceGenerator 源生成器每次全量运行，在 Windows 上同样发生。50s/200s 的大数字全是冷启动：首次 NuGet restore + MSBuild/SDK 的 JIT 预热 + 首次全量编译。缓存全热后收敛到 2.63s。

排查方法论记下来：time 拆 user vs sys。sys 高 = 文件系统/内核瓶颈（9p 的典型症状）；user 高 = CPU/编译瓶颈 [S1]。Phoronix 在 Windows 11 WSL2 对裸机 Ubuntu 的基准里给出同样结论：CPU 开销 minimal，I/O 是相对裸机的主要慢点 [S7]。

误区二：「轻操作在哪都差不多」——半真

单次 grep/read/edit，三方都是亚秒级，/mnt 也能忍 [S1]。一旦上量——write1000、git status、build——/mnt 立刻崩盘。轻操作掩盖了协议税，直到一次 npm install 或全量编译把你打回原形。

陷阱三：WSL 的表象全是陷阱——黑洞连接也能「成功」

这是我这次最贵的教训。公司内网有个 MySQL 实例，不在公司 VPN 放行的网段，任何真实 IP 直连都是黑洞：连接被吞，没有响应。问题在于——黑洞连接也能完成 TCP 三次握手 [S13]。

exec 3<>/dev/tcp/host/port && echo TCP-OK——这条命令在黑洞上照样打印 TCP-OK。我的 v2、v3 两版网络方案，回归测试全报"正常"，MySQL 其实从来没连通过。直到 v4 我改用 python 读 MySQL 握手包、以实际业务请求通断为准，才第一次看到真正的握手成功 [S13]。另外一个坑：bashrc 残留的 http_proxy 会让 curl 直连 127.0.0.1:7897 绕过 TUN，造成"方案通了"的假象 [S13]。

验证纪律

TCP 三次握手能完成 ≠ 连接真的通了。黑洞连接也能握手——验证必须看真实业务效果（读握手包、跑实际请求），而不是看"看起来成功"。

两个领域，同一个教训：性能要拆 user/sys 看瓶颈，连通性要读握手包看真通。WSL 环境里的"看起来正常"，多半是骗你的。

四、不是个例：跨语言生态同款模式

2019 年 vxlabs 的实测：yarn build create-react-app，WSL2 访问 NTFS 用了 63.14s，WSL2 原生 ext4 只要 5.8s（原生 Linux 4.63s）[S2]。同文结论：WSL2 访问 NTFS 比 WSL1 还慢约 5 倍。

Stack Overflow 高赞问答里，9p 协议被直呼 "insanely slow"，把项目移进 Linux 文件系统后是 "immediate, drastic performance improvement" [S9]。Microsoft WSL 官方讨论区 #9068，Java 开发者反馈"只有 Maven 构建时慢"，workaround 是 rsync 同步 + 用 git ls-files 排除 target 目录 [S10]。

还有个独立佐证：allenkuo 的 9P vs Samba 基准，\\wsl.localhost 经 9P 在高负载下出现 "extreme latency and even system crashes" [S8]。崩溃不是我机器的个例——我这边 build 卡死，那边系统崩溃，同一个协议，同一种死法。

Julia 社区把共识说得最清楚：WSL2 性能接近原生（Type 1 hypervisor），前提是留在 VHD 内的 Linux 文件系统；一旦读写 /mnt/c 就 "slow down tremendously" [S12]。yarn、npm、Maven、.NET——四个语言生态，同一个小文件洪流模式。

五、未来会变好吗：virtiofs 的现状

官方默认至今仍是 9p，virtiofs 只是 opt-in（.wslconfig 里设 virtiofs=true）[S6]。virtiofs 用共享内存减少序列化开销，接近原生，但仍有差距：HN 上 tonymet 实测 hugo 编译，原生 WSL FS 50s vs virtiofs 75s，慢约 50% [S3]。

方向是明确的：微软新推的 WSL container 已把 virtiofs 作为默认文件系统，官方称 Windows 文件访问快 2 倍 [S11]。但两件事让今天的建议依然成立：其一，我的机器 .wslconfig 没开 virtiofs，默认还是 9p，169× 就是在 9p 下测得的 [S13]；其二，virtiofs 官方口径也只有"2 倍"，离原生仍有数量级差距 [S11] [S3]。

六、实操建议

移项目，三步，一次搞定 [S1]：

# 1. 把项目从 C 盘拷进 WSL 原生文件系统（只做一次）
cp -r /mnt/c/Dev/my-project ~/work/my-project

# 2. 编辑器/agent 走 Remote-WSL 进 ~/work 工作
#    VS Code: Remote-WSL 扩展；opencode: 在 WSL 里启动

# 3. 验证：连跑两次 build，第二次才是稳态
cd ~/work/my-project && time dotnet build && time dotnet build

不想移也行：项目留在 C 盘、工具跑在 Windows 原生，warm build 4.23s，轻操作完全够用 [S1]。但请记住：WSL 里通过 /mnt/c 访问项目是唯一的禁止项——编辑时一切正常，一 build 就废，这是最隐蔽的坑。

适合谁

重操作型（构建/安装/agent 全量扫描）→ 必须进 ext4；纯轻编辑型（偶尔 build）→ Windows 原生也可；唯一不能选的是 /mnt 桥接。

下次觉得慢，按这个 checklist 过 [S1] [S13]：

  1. pwd——项目是不是在 /mnt 下？是 → 移到 ~/work。
  2. time dotnet build——看 user vs sys。sys 高 → 文件系统问题（多半是 /mnt）。
  3. 冷热区分——连跑两次，第二次才是稳态。第一次慢是 restore + JIT 预热，正常。
  4. 源生成器——无改动 build 也固定慢几秒 → 源生成器全量运行，Windows 上一样，不是环境问题。
  5. 网络排查——别信 TCP-OK，用真实业务请求（读 MySQL 握手包 / 实际 curl 业务接口）验证连通；先 unset http_proxy https_proxy HTTP_PROXY HTTPS_PROXY 排除环境变量干扰 [S13]。

七、最后

项目放哪，是 AI 编程时代最便宜的优化：一次 cp，换来两个数量级和「不崩溃」。

今天就把项目移进 ~/work，连跑两次 build，用第二次的耗时做基线。以后谁再跟你说"WSL 慢"，把 time 的拆解甩给他看。
